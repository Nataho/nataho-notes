Lavhanan Laundry Hub — Project Assistant

A restricted chat window where the team can ask this model about the project, upload source files, keep the paper notes in sync, and publish through a confirmation phrase.

  • Local chat: http://127.0.0.1:8002/assistant
  • Public chat (Tailscale Funnel): https://hashinata.tadpole-cliff.ts.net/assistant
  • Owner inbox: http://127.0.0.1:8002/admin/assistant (or the same path on the funnel)
  • Branch: experiment/assistance-ai
  • Context: Lavhanan Laundry Hub - System Context · Lavhanan Laundry Hub - Build Plan · Lavhanan Laundry Hub - Final Requirement Document

Who can use it

Only accounts with ROLE_TEAMMATE can open /assistant. Admins also pass through the role hierarchy for testing. Customers and shop staff get 403.

AccountNamePassword
owen@lavhanan.testOwen N. Estreralavhanan123
sam@lavhanan.testSam Rich John L. Orcullolavhanan123

The owner creates the remaining teammate accounts from Admin → Accounts → New account → Team Member when the rest of the names arrive.

What it does

  • Answers project questions from the five notes.
  • Suggests what is missing using the checklist and progress note.
  • Accepts PDF, DOCX, TXT, MD, and image uploads (no videos; max 3 files, 10 MB each).
  • Extracts PDF/DOCX text with Python (pypdf / python-docx); images go to the model directly.
  • Can patch only these three notes:
    • Lavhanan Laundry Hub - Final Requirement Document.md
    • Lavhanan Laundry Hub - Final Requirement Checklist.md
    • Lavhanan Laundry Hub - Final Requirement Progress & Context.md
  • Cannot edit System Context.md or Build Plan.md; it suggests changes to the owner instead.
  • Can add a message to the owner inbox when the team asks it to contact the owner.
  • Generates a 3-word confirmation phrase when a publish is requested. The phrase is server-generated, one-time, and expires in 10 minutes. On the correct reply it runs @export_update, then compacts the conversation and keeps the thread open.

How it is built

Chat

  • Symfony route /assistant + templates/assistant/index.html.twig; brand colors, mobile layout, file upload.
  • Stimulus controller assets/controllers/assistant_chat_controller.js keeps the thread live:
    • polls /assistant/status every 5 seconds while idle and every 2 seconds while a reply is pending,
    • reloads when the last message id changes, the last status changes (pending → done), or a visible “Working…” bubble is no longer pending,
    • the status endpoint returns only last_id, last_status, and pending — it does not hydrate message contents,
    • pauses while the tab is hidden and checks immediately when it returns,
    • saves the draft and scroll position across reloads,
    • Enter sends, Shift+Enter adds a newline,
    • paste a screenshot or file anywhere on the chat page, or drag files in; the browser validates type/size/count and shows an attachment tray with thumbnails and remove buttons,
    • re-attaches up to 3 recent images (current message first, then the most recent earlier messages) so a follow-up can ask about a screenshot sent in a previous turn; the same images go to both judges and the revision pass,
    • wraps Markdown tables so wide tables scroll inside the message,
    • adds a copy button for the publish phrase.
  • A right-side Goal & progress rail shows the project goal, a document-snapshot progress bar (done / in progress / not started), the checklist count, missing-marker/open-question counts, and the teammate's personal My to-do list. To-dos are added only when the teammate explicitly asks; the assistant never dumps the whole checklist into the rail.
  • Personal to-dos live in the assistant_goals table (goal_add / goal_done / goal_replace model actions); the teammate can tick or remove them directly in the sidebar. goal_replace swaps the whole list when the teammate asks to change it, and an approved screenshot automatically marks its matching personal to-do done.
  • The header shows a Live/Offline indicator and a manual Refresh button.
  • Messages, attachments, publish requests, and audit events are stored in MySQL (assistant_* tables).
  • A Messenger worker handles the model call and the publish job:
    bash
    symfony console messenger:consume async

Model

  • Tool-less OpenCode agent .opencode/agents/project-assistant.md, model opencode-go/deepseek-v4.1-flash.
  • Symfony calls opencode run --agent project-assistant --format json --archived --file <context.md>; the notes and conversation are attached as a context file so Windows command-line limits are never hit.
  • The model returns only JSON:
    json
    {
  "reply": "...",
  "note_patches": [{"file": "draft", "old": "...", "new": "..."}],
  "request_publish": false,
  "owner_message": null,
  "goal_add": [],
  "goal_done": [],
  "goal_replace": []
}
  • The model has no tools: no shell, no file access, no browser, no git. Symfony validates and applies every action.

Two judges

Before a reply is accepted, two independent critic passes run on the same model with different biases:

  1. Fidelity judge — checks claims against the notes/uploads; catches invented facts, citations, contradictions.
  2. Consistency judge — checks the draft ↔ checklist ↔ progress sync; catches stale ticks, missing updates, promised changes with no patch.

Both judges return two separate verdicts: one for the note patches and one for the reply wording. A patch is blocked only when it contradicts the notes or invents facts; a reply that contradicts the paper is withheld, but a correct patch still applies. Missing sections and partial drafts are not reasons to block a patch or a publish.

If either verdict fails, the assistant gets one revision round with the issues. If the patch verdict still fails, the changes are not applied and a judge-conflict event goes to the owner inbox. If only the reply verdict fails, the patches apply and the unsafe reply is replaced with a short notice listing the issues.

Both judges receive the recent conversation (last 40 messages), the compacted memory, the current request, and the proposed reply/patches. Facts the teammate states about themselves or the project in chat are valid evidence; the judges only flag them if they contradict the notes. This lets “my name is X” in one turn be applied by “apply that” in a later turn.

Notes sync

  • Exact old → new patches only; old must appear exactly once.
  • symfony/lock guards the notes; every change writes a timestamped backup under var/assistant/backups/.
  • The note-change event stores a line diff and the backup path, so the owner can review the exact edit and revert it from /admin/assistant.
  • The checklist and progress note are updated together with the draft; they are not allowed to drift.

Publish

  • Publishing updates the notes website, not the final paper. Partial notes can be published while [MISSING] sections remain; the assistant must say what is still missing and must not claim the paper is final.
  • The phrase is generated server-side (AssistantMagicWord), stored as a password hash, expires in 10 minutes, one use only.
  • On a correct phrase, PublishNotesMessage runs the existing export_update helper under a lock.
  • Success: publish event in the owner inbox, commit hash recorded, context summarized and the thread continues.
  • Failure: the team is told to contact the owner; a failure event is added to the owner inbox. No email is configured.

Owner inbox

/admin/assistant shows:

  • teammate messages the AI was asked to send,
  • publish successes and failures,
  • note-change audit with an exact line diff and a Revert this change action backed by the timestamped backup,
  • judge conflicts,
  • all conversations and message history.

Mark messages read from the inbox. No SMTP is required.

Gotchas

Environment and behavior notes
  • php_fileinfo is not available in this PHP build. Upload validation is extension-based; files are stored outside the web root and never executed.
  • Teammates must be excluded from isCustomer() and redirected in both HomeController and AppAuthenticator; otherwise login sends them to /orders (403) or the customer portal.
  • The Messenger worker must be running for chat replies and publishing. async is sync:// in tests only.
  • A long-running dev worker leaks memory: Doctrine's debug backtrace holder exhausts PHP's 128 MB limit after ~1.5 hours of polling. Run the worker in prod mode with headroom:
    php -d memory_limit=512M bin/console messenger:consume async --env=prod --memory-limit=384M
  • Judges at #high reasoning were too slow (~3 minutes). They use #low; a full live reply took ~64 seconds with two judges.
  • opencode run --format json outputs JSONL; parse only type: text events. --file attaches the context file and images; the model has no read tool.
  • Tables need GitHub-flavored Markdown; the core CommonMark converter renders pipes as plain text. The app uses GithubFlavoredMarkdownConverter.
  • Blocked replies now start with Nothing was changed, and the model is instructed to phrase edits as proposals. Judges receive chat history so a name given earlier can be applied by a later “apply that”.
  • Judge verdicts are split: patch issues block the edit, reply issues only withhold the reply. This stops a wording error from discarding a correct patch.
  • Publishing the notes site is allowed while [MISSING] markers remain; only contradictions, invented facts, and draft/checklist/progress drift are blocked.
  • The old inline chat poller only ran when the page rendered a pending message; Turbo form submissions replaced the body without re-running the head script. The new Stimulus controller reconnects after Turbo navigation and polls by last_id, so new replies appear without a manual refresh.
  • Personal to-dos are opt-in: goal_add is only populated when the teammate says “add this to my goals” or similar. goal_replace is used when they ask to change/replace the whole list; it removes the old goals and adds the new list. The assistant must not add the whole checklist or all missing items.
  • The sidebar’s main bar uses the progress note’s Snapshot (✅ done, 🟡 in progress, ⬜ not started). The checklist count is separate because checklist ticks only happen when the item is in the Word file — so it can sit at 0/127 while the draft is well advanced.
  • A “replace the list” request previously only added the new items and left the old aggregate open. goal_replace now clears the old list first; the reply must not claim it was replaced — Symfony appends the confirmation.
  • When the teammate sends a screenshot/file that matches a personal to-do and the assistant judges it acceptable, it marks that to-do done automatically. The shared checklist still ticks only when the content is in the Word file.
  • phpunit.dist.xml sets memory_limit=512M; the persistent test DB has grown enough that the default 128M can end the PHP process mid-suite.
  • The demo seed originally found an existing customer account at sam@lavhanan.test; the seed now upgrades it to ROLE_TEAMMATE and updates the name.
  • The test DB keeps rows between runs; assistant tests use a temp notes directory (var/assistant/test-notes) and a fake model runner (FakeAssistantModelRunner).
