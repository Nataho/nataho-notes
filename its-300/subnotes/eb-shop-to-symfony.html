EB Shop to Symfony

#notes#webdevLast updated: Nov 7, 2026

Migration guide for the old pure-PHP shop: take the eb_shop database, rebuild it fresh on Docker + MySQL 8, and wire it into the Symfony project.

Related: Symfony and Docker

Context
  • source database: eb_shop on XAMPP MariaDB 10.4.32 (127.0.0.1:3306, user root, no password)
  • target: Docker compose stack in the format from Docker — eb-mysql (MySQL 8.0) + eb-phpmyadmin — kept blank; data gets entered by me, not the AI
  • project: C:\Users\Nataho\Documents\school\webdev\symfony\finals — Symfony 8.1, PHP 8.4, Doctrine 3, maker-bundle present
  • work split: I run every command, the AI writes the code. the tables below tell me what to type at every prompt.

TL;DR — run order

  • 1. disable compose.override.yaml (rename by appending -disabled, per Docker)
  • 2. replace compose.yaml with the professor's format (eb-mysql + eb-phpmyadmin)
  • 3. netstat check that 6967/6969 are free; remove stale manual EB_* containers if still around
  • 4. update .env — adds MYSQL_ROOT_PASSWORD, app user, port 6967, serverVersion
  • 5. docker compose up -d → verify both containers Up + phpMyAdmin alive at :6969
  • 6. check Symfony can reach the DB (dbal:run-sql)
  • 7. make:entity × 4 → Product, Order, OrderItem, Image (User already exists)
  • 8. pin table/PK/FK names on all entities (started as one line on Order — see Step 3)
  • 9. make:migration → reviewed → migrate ✅ (Version20261107065721)
  • 10. doctrine:schema:validate → mapping valid + in sync
  • 11. put data in (me — phpMyAdmin ships in the stack now)

run everything from the project root:

bash
cd "C:\Users\Nataho\Documents\school\webdev\symfony\finals"

Step 1 — compose.yaml in the professor's format

the Symfony recipe's compose.yaml runs PostgreSQL 16 with a random exposed port, and a compose.override.yaml stacks on top of it — none of that matches the format from Docker: two containers (MySQL + phpMyAdmin), explicit container_names, one named network, one named volume, ports fixed at sensible numbers. swap both files out.

1a — disable the override

IMPORTANT — from the notes

change your compose.override.yaml to compose.override-disabled.yaml or basically delete it so that it doesn't interfere with your development.

bash
Rename-Item compose.override.yaml compose.override-disabled.yaml
side effect: Mailpit leaves the stack

the override was the only thing running Mailpit. fine for the shop — .env has MAILER_DSN=null://null anyway.

1b — replace compose.yaml

replace the entire contents of compose.yaml with this (same shape as Docker §Using compose.yaml: it creates two containers named eb-mysql and eb-phpmyadmin, images in the name):

yaml
services:
  eb-mysql:
    image: mysql:8.0
    container_name: eb-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: ${MYSQL_DATABASE}
      MYSQL_USER: ${MYSQL_USER}
      MYSQL_PASSWORD: ${MYSQL_PASSWORD}
    ports:
      - "6967:3306"
    volumes:
      - eb-db-data:/var/lib/mysql
    networks:
      - eb-network
  eb-phpmyadmin:
    image: phpmyadmin
    container_name: eb-phpmyadmin
    restart: unless-stopped
    environment:
      PMA_HOST: eb-mysql
    ports:
      - "6969:80"
    networks:
      - eb-network

volumes:
  eb-db-data:

networks:
  eb-network:

those ${...} placeholders are read straight from the project's .env — that's the whole trick from the notes. the old recipe also left behind a volume called database_data (PostgreSQL data files); nothing references it now, so it just sits unused — leave it, or clean it: docker compose down then docker volume rm finals_database_data.

1c — before up: check ports + stale containers

XAMPP's MariaDB is on 3306 — that's why the compose maps 6967/6969 instead. the notes' habit applies: know what's listening before binding (netstat prints nothing when the port is free):

bash
netstat -ano | findstr 6967
netstat -ano | findstr 6969

if the personal manual-run containers from Docker (EB_mysql, EB_phpmyadmin) are still around, remove them first — they're registered on the same host ports and names can clash:

bash
docker rm -f EB_mysql EB_phpmyadmin

1d — up + verify + lifecycle

DISCLAIMER

the following commands WILL NOT WORK if the terminal you are using is NOT inside the root folder of your project.

bash
docker compose up -d
docker compose ps    # expect eb-mysql & eb-phpmyadmin, both "Up"
docker exec -it eb-mysql mysql --version    # expect 8.0.x

optional — inspect the network the compose file created (both containers should appear as endpoints on it):

bash
docker network inspect eb-network

phpMyAdmin answers at http://localhost:6969 — log in with the MYSQL_ROOT_PASSWORD from .env (or the ebuser account for day-to-day work).

the compose lifecycle from the notes:

bash
docker compose stop      # stops both, containers stay registered
docker compose down -v   # stops AND wipes containers + eb-db-data (blank start again)
down -v deletes whatever data you typed into phpMyAdmin

use stop for day-to-day shutdowns. down -v = reset-to-blank; only when you want the DB re-seeded. -v = vanishes — it never saves; it erases.

1e — wipe-day recovery loop (for when down -v is the class norm)

if the workflow wipes regularly, recovering is a standard loop, not a panic: migrate rebuilds the structure, the seed file rebuilds the contents.

eventwhat's in the volumewhat I do
first-ever up -dempty eb_shop, zero tablesdoctrine:migrations:migrate — once
stop / down (no -v) / reboot / closing appsvolume survives — schema and rows intactnothing
down -v → up -dblank again (Docker auto-creates empty eb_shop from .env)migrate (structure) + seed import (rows)
running migrate when already migratedthe doctrine_migration_versions table inside the DB stamps what's doneprints Nothing to migrate — always safe to re-run
mental model

entities = blueprint code — they never "run". the migration is the to-do list SQL generated from them, executed only on a blank database; the stamp lives inside the database itself, which is why the same file rebuilds it identically every wipe.

powershell
# 1. structure — always first, always safe to re-run
symfony console doctrine:migrations:migrate --no-interaction

# 2. contents — after the migration, pour the seed file back in
Get-Content .\eb_shop_seed.sql -Raw | docker compose exec -T eb-mysql mysql -u root -pebRootPass1 --default-character-set=utf8mb4 eb_shop

(GUI alternative: phpMyAdmin → Import tab — same result.)

the seed file is made once, whenever the data looks good, and re-made whenever you've typed more:

powershell
docker exec eb-mysql mysqldump -u root -pebRootPass1 --default-character-set=utf8mb4 eb_shop > eb_shop_seed.sql

(phpMyAdmin route: eb_shop → Export → Save — identical outcome.)

the seed file holds password hashes + emails

keep it OUT of the git repo. store it beside the vault notes, or in the project root after eb_shop_seed.sql is in .gitignore.

Step 2 — .env

the professor-format compose pulls four values straight from this file (MYSQL_ROOT_PASSWORD, MYSQL_DATABASE, MYSQL_USER, MYSQL_PASSWORD), and the DATABASE_URL at the bottom already interpolates MYSQL_* for Symfony itself — so this one file feeds both worlds:

keyXAMPP valuenew value
MYSQL_ROOT_PASSWORD—new key — e.g. eb_root_cap — the container's root password, used for in-container admin + phpMyAdmin root login
MYSQL_USERrootebuser — a dedicated app user, NOT root
MYSQL_PASSWORD(empty)the ebuser password — this is what Symfony connects with
MYSQL_IP127.0.0.1keep
MYSQL_PORT33066967 (compose maps it)
MYSQL_DATABASEeb_shopkeep
root vs app user

root (MYSQL_ROOT_PASSWORD) is for inside-the-container admin work and phpMyAdmin root logins. the app itself talks through ebuser — same split the notes bake into their compose block.

and bump the server version in the DATABASE_URL line — MariaDB → MySQL:

env
DATABASE_URL="mysql://${MYSQL_USER}:${MYSQL_PASSWORD}@${MYSQL_IP}:${MYSQL_PORT}/${MYSQL_DATABASE}?serverVersion=8.0.36&charset=utf8mb4"
password with special characters

DATABASE_URL is still a URL — characters like @ : / ? # inside the password must be percent-encoded (e.g. @ → %40). plain alphanumeric passwords avoid the whole issue.

sanity checks before making entities:

bash
symfony console dbal:run-sql "SELECT 1"    # optional, but catches a wrong .env before make:entity does
docker exec -it eb-mysql mysql -u root -p -e "SHOW DATABASES;"    # eb_shop should exist

Step 3 — entities via make:entity

how to read these tables
  • run the command, then follow the rows top to bottom. Enter = just press enter to accept the bracketed default.
  • make:entity auto-creates the id field on every new entity — and it lands as a plain id column, not *_id (learned the hard way: the first migrate died because FKs pointed at users.id, which doesn't exist). after the run the AI pinned every PK with #[ORM\Column(name: ...)] → product_id, order_id, item_id, image_id — one-line edits, nothing to type in the terminal.
  • naming strategy in config/packages/doctrine.yaml is underscore, so camelCase properties auto-map to snake_case columns (userName → user_name). no need to type column names anywhere.
  • wording of prompts can differ slightly between maker versions — match by meaning.
  • watch the "new field name inside entity" prompt — it arrives right after answering "add a property on <Other> yes". that's naming the collection on the OTHER class ($user->getOrders()), not a field of yours. the bracketed default (orders, orderItems) is the one the doc expects → press Enter.

User — already exists, skip it

src/Entity/User.php is already set up (security-bundle style) and mapped to users:

then pin the identifiers (AI-applied after make:entity — all five entities got the full treatment in the end):

php
#[ORM\Entity(repositoryClass: OrderRepository::class)]
#[ORM\Table(name: 'orders')]                    // ← table pin (already in this step)

why that line matters

order is a reserved word in MySQL. the XAMPP table is named orders (plural), and Doctrine's underscore naming would default the new entity to table order. this single line pins the table name so the migration generates orders cleanly.

two small differences vs XAMPP
  • XAMPP had a unique key on filename. to keep it, add unique: true to the column attribute (one-line code change — the AI can do it after entities are made).

Step 4 — migrations (blank DB, so this runs for real)

bash
symfony console make:migration

open the generated file in /migrations/ and skim it. expected content:

  • CREATE TABLE for product, orders, order_item, image (+ users if the users table isn't there yet)
  • foreign keys on orders.user_id, order_item.order_id, order_item.product_id, image.uploaded_by
  • unique index on users.user_email
  • all columns snake_case — if any come out camelCase, something ate the naming strategy; stop and check doctrine.yaml
review before running

on this fresh database the migration should only contain CREATE/ADD statements. any DROP/RENAME is a red flag — read it before running.

bash
symfony console doctrine:migrations:migrate

confirm with yes, then validate:

bash
symfony console doctrine:schema:validate

expected tail: [OK] The ORM mapping of the entity classes is valid. and [OK] The mapping on the database is in sync with the current mapping metadata. — on a blank DB freshly migrated, both should pass clean.

do NOT import the XAMPP dump before migrating

the flow is entities → migration → migrate on an empty schema. importing SQL first (the old-phpMyAdmin reflex) makes make:migration produce conflicting drop/alter diffs against what came in. entities first, migrate second, data last.

Appendix — importing the old data (optional, mine to own)

two ways in. the GUI way (phpMyAdmin at http://localhost:6969) or the SQL way:

powershell
# 1. dump from XAMPP
& "C:\xampp\mysql\bin\mysqldump.exe" -h 127.0.0.1 -P 3306 -u root eb_shop > eb_shop.sql

# 2. load into the docker MySQL (commands from project root)
Get-Content .\eb_shop.sql -Raw | docker compose exec -T eb-mysql mysql -u root -p<MYSQL_ROOT_PASSWORD> --default-character-set=utf8mb4 eb_shop
enter data through phpMyAdmin instead

if the data goes in by hand (no dump), phpMyAdmin is the friendliest route — and order matters for the FKs: insert users first, then products, then orders + order_items (they reference those), then images (uploaded_by is nullable so it can come last). keep orders.total_amount consistent with its line-item math — the old rows did.

dump ↔ entity schema friction

the XAMPP users row sizes (255/255/255) exceed the existing entity's user_name(100) / user_email(180) — long values would truncate, and the fresh unique-email index bites if a duplicate sneaks in. current data fits, but decide consciously (import as-is vs. have the AI bump lengths first).

MariaDB 10.4 → MySQL 8.0 dump compatibility

the dump usually imports clean (both are utf8mb4, no exotic storage types here), but the MariaDB current_timestamp() default on uploaded_at is worth watching — MySQL 8 accepts it, yet nullability/precision can shift slightly. verify row counts after import:

bash
docker exec -it eb-mysql mysql -u root -p<MYSQL_ROOT_PASSWORD> -e "SELECT COUNT(*) FROM eb_shop.orders;"

the test database — one-time provisioning

why eb_shop_test

the doctrine recipe's when@test block (dbname_suffix: '_test') makes every test target eb_shop_test so tests never touch real data. but the docker entrypoint only grants ebuser rights on eb_shop, so the test schema needs a one-time setup (done ✅):

bash

the same migration file builds both schemas — free reproducibility proof for the exam.

lessons burned into the code (don't relearn them)
  • invalid form submissions return HTTP 422, not 200 — modern Symfony; the tests assert assertResponseStatusCodeSame(422).
  • the header partial's <h1> is the first h1 on every page — test selectors must scope (.auth-card h1).
  • if an entity file vanishes mid-session (src/Entity/Order.php did, and it broke mapping everywhere), git restore <path> resurrects it byte-exactly from the last commit.
  • a push failing with GH001: Large files detected means the blob is inside history, not just the folder — deleting the file alone won't help. surgical fix: git filter-branch --index-filter "git rm --cached --ignore-unmatch '<big file>' '<other big file>'" -- --all, then delete the refs/original backups + git reflog expire --expire=now --all + git gc --prune=now, then push again. this alone took the finals repo from 205 MB to 13.75 MiB.
  • phpunit died at booting cascade style when the first test's cleanup crashed — fix the root error first, the rest is noise.
  • #[Autowire(param: 'kernel.project_dir')] — the param name goes bare, no %-wrapping. a %kernel.project_dir% string sneaked in and the container handed the service the unresolved literal, so every upload landed in a junk folder literally named %kernel.project_dir%/... while the DB row happily said "success" (found by a test that checked the file actually exists on disk).

lessons burned into the code (don't relearn them)

Phase 2 debug round — one 500 below six failures, then three real findings
  • a twig {% include %} only inherits context vars by NAME. the controller renders is_banned, the partial reads banned — nothing passes it, so every shop GET with products 500'd with Variable "banned" does not exist. fix: {% include 'partials/shop/_product_card.html.twig' with { banned: is_banned } %}. six failing tests were one cascade (no modal, no badge, no grid are downstream symptoms of the 500).
  • the second add-to-cart died because of symfony/ux-turbo drive, not the hot reload morpher. turbo ships with the webapp recipe, intercepts the cart form submit and swaps the body SPA-style — on the swapped-in page it re-executes every inline script in the same global scope, so let currentProductPrice / const ConfirmModal from page 1 already exist → SyntaxError: Identifier has already been declared during body.replaceWith → the new page lands half-swapped with no bindings at all ("first click works, whole page dead after"). fix: one attribute on the body in base.html.twig — data-turbo="false" — turbo checks closest("[data-turbo]") per interaction, "false" ⇒ full browser navigation = the old site's behavior, fresh globals every load. lesson: this port's scripts are full-page-load code; SPA body-swapping tools (turbo) fight them by design. the frankenphp hot-reload/idiomorph block removed earlier was defensible page-weight cleanup, but it was NOT the bug.
  • AssetMapper hashes filenames on the page (1.png → 1-eCvNprM.png) — tests must match the pattern (#/assets/images/1-[a-zA-Z0-9_-]+\.png$#), never the bare filename. and the hash alphabet includes _.
  • post-redirect error flashes render in the alert modal, not in a page block — scope them #shopAlertModal .confirm-modal-message. .account-alert.err is the persistent strip (always present for banned users), so assertSelectorTextContains grabs it first and comparisons misfire.
  • --ignore-cr-at-eol in git diff instantly separates real edits from line-ending churn — the working tree looked like 33 modified files; the real content diff was 3 + new files.
